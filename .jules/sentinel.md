## 2026-08-12 - `bearer:disable` Suppressions Silently No-Op if the Justification Shares the Directive Line
**Vulnerability:** N/A (CI hygiene, not a runtime vuln) — my own fix for the DNS-rebinding SSRF re-triggered a Bearer `javascript_lang_logger_leak` alert on `server/pushNotifications.ts` even though I'd added a `bearer:disable` comment right above the `logger.warn` call.
**Learning:** I wrote `// bearer:disable javascript_lang_logger_leak — subId is a uuid, no secrets`. Bearer's parser takes *everything after* `bearer:disable` on that comment line as the comma-separated rule-id list (plain `strings.Split` + `TrimSpace`, no tokenization) — the `— justification` suffix becomes part of the "rule id" and the suppression never matches anything, so the alert fires anyway. This exact mistake has been made and re-fixed at least 6 times in this repo's history (commits 1bdbae03, cf7c06ea, 2e68daa1, 8785521f, 3195d249, 9e7fec55) — it's an easy trap because every other comment convention in this codebase puts the "why" inline with the directive.
**Prevention:** `bearer:disable <rule_id>` must be the ENTIRE content of its comment line — no trailing `—`/justification text, nothing else. Put the justification on its own comment line directly ABOVE the bare directive line, which itself sits directly above the flagged call:
```ts
// subId is a uuid, no secrets.
// bearer:disable javascript_lang_logger_leak
logger.warn({ subId: sub.id }, "...");
```
Grep `bearer:disable.*—` (or any trailing text after the rule id) before pushing any new logger-leak suppression — if it matches, the suppression is silently dead.

## 2026-08-12 - A "Fixed" SSRF PR Can Still Ship the Regression: Verify the Merged Diff, Not the Commit Message
**Vulnerability:** `server/pushNotifications.ts` had zero DNS-rebinding protection at send time — `sendToSubscription` called `webpush.sendNotification(pushSubscription, ...)` directly on `sub.endpoint` with no re-validation, despite PR #1757 ("🛡️ Sentinel: [HIGH] Fix SSRF via DNS rebinding in push notifications", merged into main) claiming to have fixed exactly this.
**Learning:** That PR was 4 commits from a *different* automated agent (`google-labs-jules[bot]`), all with the identical templated commit message, pushed ~10-30 min apart. The first commit (747eb4a) genuinely added `assertResolvedHostIsPublic(sub.endpoint)` before the send call. The last commit (9804cf8) — likely an unrelated formatting/lint pass — deleted both the import and the call while reusing the same "Fix SSRF via DNS rebinding" message and the same "🔧 Fix: Added a DNS resolution check..." body. The PR merged with the *first* commit's message still describing behavior the *last* commit had silently reverted, and no test caught it because no `pushNotifications.test.ts` existed to pin the behavior. Root cause: `checkSafeOutboundUrl` (used by `routes/push.ts` at subscribe time) only catches literal private IPs in the URL string — it cannot catch a hostname that resolves to a public IP at subscribe time and gets re-pointed at an internal address before the next send, which can happen long afterward since sends are triggered by unrelated app events, not the subscribe flow.
**Prevention:** When a git-log title claims a security fix, diff the merged tree against `main`, not just read the commit message — multi-commit PRs (especially from other bots/agents) can regress themselves between the first and last commit while the message stays stable. Any endpoint that accepts a user-supplied outbound URL and calls it later (not immediately) needs the DNS-rebinding check (`assertResolvedHostIsPublic`) at the point of actual use, not only at intake — `checkSafeOutboundUrl` alone is a intake-time filter, not a send-time guarantee. Added `server/pushNotifications.test.ts` to pin this (mocks `ssrfGuard`/`web-push`/`storage`, asserts the guard is called before `sendNotification` and that a rejection removes the subscription without sending) so this exact regression fails CI next time instead of merging silently.

## 2026-05-11 - Standardize Input Validation via Middleware
**Vulnerability:** Inline `zodSchema.safeParse` in Express routes bypasses standardized schema validation structures.
**Learning:** By utilizing `validateBody(schema)` in the route middleware definitions, the project ensures all API routes return a consistent error signature on invalid input (`{ code: "VALIDATION_ERROR", message: string, details: ... }`), preventing internal validation details or edge cases from leaking unexpectedly. Using `Request<..., ..., z.infer<typeof schema>>` ensures `req.body` is appropriately typed within the handler.
**Prevention:** Always use `validateBody`, `validateQuery`, and `validateParams` middlewares from `server/routeUtils.ts` rather than inline `safeParse` for request validation.

## 2026-05-24 - Prevent SSRF in Web Push Subscription
**Vulnerability:** The web push subscription endpoint accepted any valid URL for the push `endpoint` field, including internal `http://` URLs.
**Learning:** When dealing with external callback URLs (like push notification subscriptions), failing to strictly enforce HTTPS allows an attacker to supply an internal IP or local domain (e.g., `http://169.254.169.254`). The server's web push library would then unknowingly make a POST request to this internal address, resulting in Server-Side Request Forgery (SSRF).
**Prevention:** Always validate that user-provided URLs intended for server-to-server outbound calls strictly start with `https://`.

## 2026-06-06 - Strengthen SSRF Protection on Web Push Endpoints
**Vulnerability:** The web push subscription endpoint required URLs to start with `https://`, but this check did not prevent internal/local network targeting if the URL used a private IP or loopback address (e.g., `https://127.0.0.1` or `https://192.168.1.1`).
**Learning:** Enforcing HTTPS alone is insufficient to prevent Server-Side Request Forgery (SSRF). An attacker could still attempt to interact with local HTTPS services or trigger internal network exploration. The `server/ssrfGuard.ts` provides a dedicated `checkSafeOutboundUrl` function to reliably detect and reject these loopback, private, and link-local addresses across both IPv4 and IPv6.
**Prevention:** When validating user-provided URLs intended for server-to-server requests, combine the protocol check with the `checkSafeOutboundUrl` guard in the Zod refinement: `.refine((url) => url.startsWith("https://") && checkSafeOutboundUrl(url).ok)`.

## 2026-06-17 - Prevent CSV Injection Bypasses via Whitespace
**Vulnerability:** The CSV export mechanism prepend-escaped fields starting with standard formula triggers (`+`, `-`, `=`, `@`, `|`) but failed to catch fields where these triggers were preceded by a tab (`\t`) or carriage return (`\r`), allowing CSV injection filters to be bypassed in spreadsheet software like Excel.
**Learning:** Spreadsheet applications often strip leading whitespace before evaluating cell contents. This means an attacker can start a field with a tab character followed by an equals sign (`\t=CMD()`), bypassing naive regex checks that only look at the first character, but still triggering formula execution when opened by the victim.
**Prevention:** Always include `\t` and `\r` in the formula detection regex (`/^[+\-=@|\t\r]/`) when validating or escaping untrusted data for CSV exports.

## 2026-08-12 - `req.auth` Is a Function Under @clerk/express v2 — Every Rate Limit Was IP-Keyed
**Vulnerability:** `server/routeUtils.ts` bucketed rate limits with `req.auth?.userId`. Under `@clerk/express` v2 the middleware attaches `req.auth` as a *function* (`Object.assign(request, { auth: brandRequestAuth(opts => requestState.toAuth(opts)) })`; `getAuth(req)` is a wrapper that calls it). A function has no `.userId`, so that branch was dead and all 135 `rateLimiter()` call sites silently fell through to IP keying — including the AI-spend limiters (`planGenerate` 3/window, `chat`/`parse` 5–10/window) and `garminConnect`, whose own comment claimed per-user keying.
**Learning:** The bug was invisible because the unit tests *encoded the stale v1 contract* — fixtures built `req = { auth: { userId: "user123" } }`, an object shape the installed library no longer produces. The tests asserted per-user bucketing and passed, while production never took that branch. A hand-written mock of a third-party request decoration is an assumption about that library's contract, and it keeps passing after a major-version upgrade silently changes it. Note the failure direction: a broken *auth* check fails loudly (nobody can log in), but a broken *rate-limit key* fails silently and open — nothing errors, quotas just stop being per-user.
**Prevention:** Never read Clerk state off the request object — `getAuth(req)` is the only supported accessor (Clerk's core-3 upgrade guide says so explicitly), and it throws when `clerkMiddleware()` hasn't run, so wrap it and fall back rather than 500. Grep for `req.auth` / `.auth?.userId` after any `@clerk/*` major bump. When a test mocks a library's request decoration, shape the fixture like the real library does (here: `auth: () => ({ userId })`) so the mock breaks when the contract does, and prefer a regression test that pins the *security property* — two users behind one IP must not share a bucket — over one that merely pins the key string.

**Corollary — auth is not available at module-scope middleware in `server/index.ts`.** `clerkMiddleware()` is mounted late, inside `registerRoutes()` → `setupAuth()`, *below* `httpServer.listen()`. Anything registered at module scope in `index.ts` (the AsyncLocalStorage request-context binding at ~line 284) therefore runs BEFORE Clerk and cannot resolve a caller at all — a second, independent reason the old `req.auth?.userId` read there was dead. Route-level middleware is unaffected: `rateLimiter` and friends are mounted inside `registerRoutes()`, after `setupAuth()`. The subtlety that makes this easy to get wrong: pino-http's `customProps` in the same file *does* call `getAuth()` successfully, because pino-http evaluates it at response-finish time, by which point Clerk has run and decorated the request. So "is auth available here?" depends on when the callback is *invoked*, not where it is *registered* — check both before assuming a userId read works.
