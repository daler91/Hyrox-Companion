## 2026-08-01 - Drizzle relational `findMany` + in-memory ownership filter = cross-user table scan

Even though this isn't a simple SELECT N+1, it is still an N+1 performance bottleneck because it executes multiple sequential DB round-trips for batch updates/inserts based on loop variables.
**Action:** When finding a `db.execute(...)` or `db.insert(...)` loop that iterates over previously fetched or computed values, replace it with a batched single-statement `db.execute` utilizing `sql.join` to consolidate all values into one multi-row insert statement.

## 2026-08-21 - An unmemoized render-body call can duplicate work a child component already memoizes correctly

**Learning:** `ReviewSurface` (client/src/components/workout-detail/ReviewSurface.tsx), the app's highest-traffic workout-detail sheet, called `buildWorkoutCoachSeedMessage(displayEntry, exerciseSets)` unconditionally in its render body — no `useMemo`. That helper copies, sorts, and groups `exerciseSets` (`groupExerciseSets` in `client/src/lib/exerciseUtils.ts`). The exact same grouping over the exact same `exerciseSets` is *already* wrapped in `useMemo` one component down, in `ExerciseTable.tsx`. `ReviewSurface` re-renders on essentially every interaction in the sheet — each debounced set-cell edit replaces the whole `exerciseSets` array reference via `patchCachedSets`'s `setQueryData`, plus RPE change, note save, delete-confirm toggle, coach-panel toggle — so this redid the grouping on renders that never even read the resulting seed text (it's only consumed if the user opens "Ask coach"). The backend-DB-shaped patterns already covered by this journal don't cover this: it's a frontend render-hygiene bug, not a query/loop shape, and the tell that it's a genuine oversight (not a micro-opt) is that a memoized copy of the identical computation already exists one level down in the same render tree.
**Action:** When auditing a React component for perf, grep for calls to helper functions that internally do `.sort()`/`.map()`/grouping over a prop-derived array, check whether the call site wraps it in `useMemo`, and — if it does — check whether an identical computation over the identical source data is *already* `useMemo`'d somewhere else in the same render tree (duplicated memoized work in a sibling/child is the giveaway this is a real, not premature, fix). Before trusting a new `useMemo`'s deps, verify each dependency is actually reference-stable across the renders you're trying to skip — a `foo?.bar ?? entry.bar ?? []` fallback allocates a fresh `[]` on every render when both operands are falsy, silently defeating both this new memo and any downstream reference-equality check (e.g. `StructureBlocksEditor`'s `normalizedValue !== trackedValue` guard, which exists specifically to avoid an expensive `JSON.stringify` deep-compare) — replace such fallbacks with a module-scope stable-empty-array constant, not a fresh literal. Also: `ReviewSurface` has an `if (!entry) return null` early return with zero hooks after it in the original code (all existing hooks — `useState`, `useWorkoutDetail`, `useMigrationReview` — sit above it); a new `useMemo` must go above that return too, even though the `key={reviewEntry?.id ?? "review-surface"}` remount trick in the parent (`TimelineWorkoutSurfaces.tsx`) makes it runtime-safe either way — `eslint-plugin-react-hooks`'s rules-of-hooks check doesn't know about that invariant and will fail lint on a hook placed after any conditional return, regardless of runtime safety.

## 2026-08-27 - Two already-parallelized fetches can still be one fully redundant round-trip, if their ranges always overlap

**Learning:** `assembleTrainingOverview` (server/services/trainingOverviewLoader.ts), which backs the most-visited Analytics tab (`GET /api/v1/training-overview`) and the AI "explain my charts" turn, already fetched `workoutLogs`/`exerciseSets` for the selected `[from, to]` window and, separately, for the trailing-70-day training-load window (`[loadHistoryStart, loadCurrentDate]`) — both inside the same `Promise.all`, so it looked already optimized by the "sequential awaits → parallel" heuristic. But `loadCurrentDate` is *always* `to ?? today`, i.e. both windows always share the same upper bound — so one window is *always* a strict superset of the other for every possible input (verified: `from` undefined → selected window unbounded, always superset; `from` earlier than `loadHistoryStart` → selected window superset; `from` later than `loadHistoryStart` → load window superset). This meant every single call issued two full relational `exercise_sets` hydrations (JSON columns, up to `MAX_WORKOUT_LOGS_PER_QUERY`=5000 logs each) where one was always fully redundant with the other. Being wrapped in `Promise.all` (parallel, not sequential) is exactly what let this hide from the earlier "sequential-awaits" sweep — the redundancy is about the *ranges*, not the *scheduling*.
**Action:** When two `Promise.all`-parallel fetches read the same table with different date/range bounds, check whether one range's bounds are *structurally* related to the other's (shared endpoint, one derived by fixed offset from the other) rather than independently user-chosen — if a shared endpoint means one is provably always a superset, fetch the wider range once and derive the narrower one with an in-memory `.filter()`, rather than two queries. Proving equivalence has to account for row caps too: `getWorkoutLogsByDateRange`/`queryExerciseSetsWithDates` both cap results at `MAX_WORKOUT_LOGS_PER_QUERY` ordered `desc(date)` (newest-first) — since truncation always drops the *oldest* rows first and the narrower window is always the "newer" sub-range of the wider one, filtering the (possibly-truncated) wide result for the narrow range is provably identical to querying the narrow range directly, even when the cap is hit. Fixed by computing which of `from`/`loadHistoryStart` starts earlier, fetching only that wider `[wideFrom, wideTo]` range, and deriving both `workoutLogs`/`allSets` (selected window) and `loadWorkoutLogs`/`loadExerciseSets` (load window) from it via `.filter(row => row.date >= ... && row.date <= ...)`. This changes the *exact* `(from, to)` args passed to the underlying storage fetchers on some inputs (e.g. `?from=2026-02-01&to=2026-02-28` now fetches `[2025-12-20, 2026-02-28]` instead of two separate calls) — tests asserting exact mock call args/counts on `storage.analytics.getWorkoutLogsByDateRange` needed updating to match (not a correctness compromise, the old assertions encoded the old, less efficient call pattern). TypeScript note: computing a boolean once (`selectedWindowIsWider`) and branching on it in two places does NOT let the compiler narrow `from` from `string | undefined` to `string` in the branch bodies — the direct condition (`from !== undefined && from > loadHistoryStart`) has to be repeated at each branch point for narrowing to apply; abstracting it into a single boolean forces a non-null assertion instead, which this codebase avoids.
